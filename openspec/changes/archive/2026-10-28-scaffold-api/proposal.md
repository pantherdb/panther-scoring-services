# Proposal

**Area:** api

## Why

`api/` is empty. The first service endpoints, and the jobs contract they rely on, need a working FastAPI app to land in: one where the project, the error format, the OpenAPI schema, lint, type checks, tests and CI are already wired. The frontend is also waiting on an OpenAPI schema to generate its types from, and it can't start that until the schema exists as a file it can read.

**Prerequisite:** `docs/design/api-stack.md` ([#7](https://github.com/pantherdb/panther-scoring-services/issues/7)) is Accepted before any code in this change is written. This change follows that doc and doesn't make the stack decisions itself.

## What Changes

- New uv project in `api/`, with its own `pyproject.toml`, `uv.lock` and `.python-version` (3.13). The Python package is `panther_api`, in a `src/` layout.
- A FastAPI app with every route under `/api/v1`, and one route: `GET /api/v1/health`, a liveness check.
- Errors as RFC 9457 problem details (`application/problem+json`) for every error the API returns: unknown routes, wrong methods, validation failures and unhandled exceptions. One `Problem` model is declared in the OpenAPI schema.
- The OpenAPI schema served at `/api/v1/openapi.json` and the interactive docs at `/api/v1/docs`, both behind the `/api` prefix that the frontend's dev proxy already forwards.
- `api/openapi.json` committed, regenerated by one command, with a test that fails when it's out of date. The frontend will generate its types from this file.
- Tooling: Ruff (lint and format, with the `S` security and `FAST` rules), basedpyright in strict mode, pytest with FastAPI's `TestClient`.
- An `api` job in `.github/workflows/ci.yml`, filling the slot left for it, and added to `ci-passed`.
- `docs/testing/api.md`: how to run the API and each check. `docs/testing/README.md` gains the `api` row in its CI table.
- `CONTRIBUTING.md`'s Spec Layout table gains the new `api-service` capability.

New dependencies: `fastapi[standard-no-fastapi-cloud-cli]` (FastAPI, uvicorn, the `fastapi` CLI and `httpx`); dev group: `ruff`, `basedpyright`, `pytest`. All are named in `api-stack.md`.

Not in this change:

- **Jobs:** `POST /api/v1/jobs`, `GET /api/v1/jobs/{id}` and the worker pool, owned by the `scoring-jobs` capability.
- **Any service endpoint** (`hmmscore`, `refmap`, `csnp`, `treegrafter`).
- **The legacy compatibility endpoints.**
- **Readiness and versions:** a check that the data and tools are present, and the data, tool and engine versions in responses.
- **The engine dependency,** since `engine/` is empty.
- **Settings:** pydantic-settings arrives with the first setting.
- **Containers and deployment.**
- **The frontend's `api:types` script.** That's a frontend change, once this one merges.

## Capabilities

### New Capabilities

- `api-service`: behaviour every API endpoint shares, whichever scoring service it belongs to: the versioned base path, the health check, the problem-details error format, and the published OpenAPI schema. Service endpoints and the job lifecycle belong to their own capabilities and follow these rules.

### Modified Capabilities

None.

## Impact

- **Code:** new files under `api/`; `api/.gitkeep` is removed.
- **Shared files:**
  - `.github/workflows/ci.yml`: the `api` job, its paths filter, and `ci-passed`'s `needs`.
  - `.gitignore`: Python caches and `.venv/`.
  - `.gitattributes`: `api/openapi.json` marked as generated.
  - `CONTRIBUTING.md`: the Spec Layout row.
  - `docs/testing/README.md`: the CI table row.
- **Docs:** new `docs/testing/api.md`.
- **Dependencies:** the Python packages listed under What Changes, locked in `api/uv.lock`. Dependabot is not configured for them, matching the npm policy in `.github/dependabot.yml`: versions change through a proposal.
- **Parity with each service's reference:** not affected. This change has no scoring logic and needs no divergences.
- **API contract:** this creates it. The frontend developer reviews the error format and the `openapi.json` workflow, which become the frontend ↔ api contract.
- **Engine:** not affected.

## Open Questions

Each needs team verification.

- **`api-stack.md` acceptance** ([#7](https://github.com/pantherdb/panther-scoring-services/issues/7)). If review changes a choice there, this change follows it.
- **Package name.** `panther_api` is the working name; the API developer confirms.
- **Public docs page.** Should `/api/v1/docs` be served in production, or only in development? The working default is always on, since the legacy CGIs have no documentation at all.
- **Dependency review and `uv.lock`.** Does GitHub's dependency graph read `uv.lock`? If not, the `dependency-review` job checks nothing for Python, and we need another way to feed it the dependencies.
- **basedpyright config.** Does `[tool.basedpyright]` in `pyproject.toml` work for both the CLI and the VS Code extension?
