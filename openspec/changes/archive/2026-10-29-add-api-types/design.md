# Design

## Context

This change relies on these decisions and doesn't repeat them:

- **API types from the schema with `openapi-typescript`, generated in CI; MSW for mocks; RTK Query for every call:** [docs/design/frontend-stack.md](../../../docs/design/frontend-stack.md), Decision and Rules That Come With It (rule 3).
- **The committed `api/openapi.json` is the contract,** so the frontend generates its types without running the API: [docs/design/api-stack.md](../../../docs/design/api-stack.md), the OpenAPI contract row.
- **Versions in every response,** so a result can be traced to what produced it: [docs/design/tech-stack.md](../../../docs/design/tech-stack.md), API recommendation 3.
- **The `Versions` shape** (`api`, `engine`, `tools: [{name, version: string | null}]`, in the engine's order): [connect-api-to-engine/design.md](../connect-api-to-engine/design.md), "The response shape".
- **How the frontend is organised:** [frontend/CLAUDE.md](../../../frontend/CLAUDE.md): features inject endpoints with `api.injectEndpoints`, tests mock at the API boundary, e2e specs are tagged by mode.

What exists now:

- `src/app/api/api.ts` creates the one RTK Query API, with `baseUrl: '/api/v1'` and no endpoints.
- `src/mocks/handlers.ts` is an empty handler list, shared by the dev server, the e2e build and Vitest. Vitest fails any request with no handler.
- `AppLayout` renders a header and `<main>`, with no footer. The e2e shell specs are untagged, because the shell made no API call.
- `.gitattributes` already marks `frontend/src/app/api/schema.d.ts` as generated by `npm run api:types`.

The behaviour is in [specs/scoring-ui/spec.md](specs/scoring-ui/spec.md).

## Goals / Non-Goals

**Goals:**

- When the API developer changes `api/openapi.json`, the frontend's CI fails until `schema.d.ts` is regenerated, and a renamed field then fails `tsc`.
- The jobs endpoints can be added as a second injected feature, with no change to the generation, the check or the store.

**Non-Goals:**

- A typed fetch client (`openapi-fetch`) or generated RTK Query hooks (`@rtk-query/codegen-openapi`). RTK Query endpoints stay hand-written; only their types are generated.
- Validating responses at runtime. RTK Query trusts the declared type; the contract check is at build time.

## Decisions

### Layout

```text
frontend/
  package.json              + openapi-typescript (dev, exact); api:types, api:types:check
  .prettierignore           + src/app/api/schema.d.ts
  eslint.config.js          + src/app/api/schema.d.ts in globalIgnores
  src/
    app/api/schema.d.ts     generated, committed
    features/versions/
      versionsApi.ts        getVersions, injected into the one API
      AppVersions.tsx       calls the query; loading and error states
      VersionList.tsx       renders a Versions value
      index.ts              exports AppVersions
    layout/AppLayout.tsx    + <footer> with <AppVersions />
    mocks/
      data/versions.ts      the mocked Versions body
      handlers.ts           + GET /api/v1/versions
  tests/features/versions/AppVersions.test.tsx
  e2e/versions.spec.ts
```

### Generating the types

`"api:types": "openapi-typescript ../api/openapi.json -o src/app/api/schema.d.ts"`, run from `frontend/`.

- **Default options.** The output has `paths`, `components` and `operations`. A feature names a schema type with an alias, `type Versions = components['schemas']['Versions']`. An alias isn't a hand-written type: renaming a field in the schema still fails `tsc` where it's used.
  - *Alternative:* `--root-types`, which also exports each schema at the top level. Rejected: the names get the generator's `Schema` prefix and casing rules, and the alias is one line.
- **From the committed file, not the running API.** Generating needs no Docker and no network, and it reads exactly what the API's own test checks against the app (api-stack.md).
- **Left out of Prettier and ESLint.** The generator has its own formatting (double quotes, four spaces). Reformatting it would make the check below fail, since it compares the generator's exact output. `tsc` still reads it; `skipLibCheck` skips checking a `.d.ts`'s own body, not its use.

### Checking it's current

`"api:types:check": "npm run api:types -- --check"`. `openapi-typescript --check` generates in memory, compares the text with the file, and exits 1 with "Generated types are not up-to-date!" when they differ. It writes nothing.

- **The same arguments as `api:types`,** because the check calls that script. The two can't drift.
- **CI's `frontend` job** runs it right after `npm ci`, in a step whose name says to run `npm run api:types`. The `frontend` paths filter adds `api/openapi.json`, so an API pull request that changes the contract runs the frontend job.
- *Alternatives:*
  - **Regenerate in CI, then `git diff --exit-code`.** Works the same, but needs a script step, and can't be run locally without changing the working tree.
  - **A Vitest test that calls the generator.** Rejected: it would repeat the CLI's options and its header comment, which can drift from the script.

### The endpoint

`features/versions/versionsApi.ts`:

```ts
type Versions = components['schemas']['Versions']

export const versionsApi = api.injectEndpoints({
  endpoints: build => ({
    getVersions: build.query<Versions, void>({ query: () => 'versions' }),
  }),
})
```

- **No conversion module yet.** frontend/CLAUDE.md puts any renaming of the API's fields in one module. `Versions` has nothing to rename, so the module waits for the first shape that needs it.
- **One request per page load.** The footer is always mounted, so RTK Query's cache keeps the result across route changes. The API answers from what it read at startup.

### Where the versions appear

**In the app shell's footer, on every page.** *(Listed as an open question in the proposal.)*

- **Why not a build detail.** The `scoring-ui` spec's "No build details on screen" forbids ports, environment variables and commands: how the app was built and where it runs. Tool and engine versions are scientific provenance. BLAST+ and HMMER versions can change which hits a score is based on (tech-stack.md, Pinning Tool Versions), and frontend/CLAUDE.md asks for them with results. The footer shows only the names and version strings the API reports, never paths; the new requirement's last scenario says so.
- **Why the footer.** It's on every page without taking space from the form or the results, and it's where users look for "about this service" information. It works before any results page exists.
- *Alternatives:*
  - **An About page.** Rejected for now: a route and a link for six values, and users comparing results across time would have to know to look there.
  - **The results page only.** Not possible yet: there are no results. When job results include `Versions`, they show the versions that produced that result. The footer keeps showing what the service runs now. Both read the same type.

### Rendering

- **A container and a list.** `AppVersions` calls `useGetVersionsQuery()` and handles loading and error. `VersionList` takes a `Versions` value and renders it. A results page can later reuse `VersionList` with a job's versions.
- **A description list** (`<dl>`): "API", "Engine", then each tool by the name the API reports, each with its version. A `null` version shows "not available". Tests read it by role (`term`, `definition`).
- **Loading and failure.** While loading, the footer says the versions are loading. On failure, it says they're unavailable, with no status or error text. It never shows an empty list. The header and page above don't wait for it.
- **Wraps at mobile width** (`flex-wrap`), so the page doesn't scroll sideways.

### Mocks

- **The mocked body lives in `src/mocks/data/versions.ts`,** typed as `Versions`, with the versions pinned in the API image. The handler in `handlers.ts` returns it.
- **The `@mock` e2e spec imports the same data** and checks the footer shows it, so a mock change can't make the spec drift.
- **Vitest overrides it per test** with `server.use(...)` for the `null` and failure cases.

### End-to-end in api mode

- **A `@api` spec** fetches `/api/v1/versions` through the page's origin with `page.request`, then checks the footer shows the same values. It hard-codes no versions, so it also works in site mode against any deployment. The pinned versions themselves are checked by the API's `api-image` CI job.
- **The shell specs stay untagged.** The footer now calls the API, but the shell specs don't assert on it; their comment changes from "makes no API calls" to "needs nothing specific from the API".

## Risks / Trade-offs

- **[Relative base URL under Vitest]** `fetchBaseQuery` builds a `Request` for `/api/v1/versions`. Node's `Request` may reject a relative URL even under jsdom. Apply finds out on the first red run. If it fails, the fix is in the test setup, not in `api.ts`: the app must keep calling a relative `/api/v1`. Record which in the Notes.
  - *Decided during apply, 2026-10-29:* it failed ("Failed to parse URL from /api/v1/versions"). `tests/setup.ts` now replaces the global `Request` with a subclass that resolves a relative URL against jsdom's `location`, as a browser's `Request` does. `api.ts` is unchanged.
- **[A contract change blocks the API's pull request on the frontend job]** That's the point of the check. The API developer runs `npm run api:types` in `frontend/` and commits the result in the same pull request; `docs/testing/frontend.md` says how.
- **[An `openapi-typescript` upgrade changes its output]** The check fails on the upgrade's pull request until `schema.d.ts` is regenerated in it. Dependabot's bump then carries a generated diff.
- **[The jobs change also changes `api/openapi.json`]** It's developed in parallel. Whoever merges second regenerates `schema.d.ts`; the check fails until they do.
- **[The footer is one more request per page load]** Small, and answered from memory. In site mode against a deployment, it's the one request the shell makes.

## Migration Plan

Nothing to migrate. Rollback is reverting the pull request.
