# HMM Scoring on Our Server, 2026-11-20

The deploy that turns on HMM scoring on our server's test site, which is reached on the university VPN ([runbook-server.md](runbook-server.md)). It has three parts: PANTHER 19's HMM library fetched into the data folder, the API image with `wire-hmmscore`, and the five `hmmscore` settings, set from a short and a long query timed on the server (#68).

- **Environment:** our server, with the API and the site behind nginx. It has 2 CPUs, 7,607 MiB of memory and 7,995 MiB of swap.
- **Date:** 2026-11-20.
- **Who:** the engine developer.

## Versions

- **The API image:** `panther-api:82a2940`, built from `main` at `82a2940` (#83, `wire-hmmscore`). It was built for `linux/amd64` on a Mac, then moved with `docker save` and `docker load`, since a build on the server can't download through its proxy ([hosting.md](../design/hosting.md#getting-the-image-to-the-server)).
- **The HMM library:** PANTHER 19's, `PANTHER19.0_hmmscoring.tgz`, sha256 `77b3a9eae1d4d1baeaf345368b861f2474893711f0187a9767397a1a1d0e87c8`, as `engine/src/panther_engine/hmmscore/data.json` pins it, under `hmmscore/19/` in the data folder. The cSNP data (frozen PANTHER 9) and the refmap data (PANTHER 19's generic mapping) are unchanged.
- **The tools, in the image:** HMMER 3.4 and BLAST+ 2.17.0. EPA-ng is as the image's lock pins it, and `treegrafter` isn't served.

## What Changed

Since the last deploy, whose API image was `panther-api:d3fbd39`, built from `main` on 2026-11-09:

- **HMM scoring runs.**
  - The API takes hmmscore jobs, with their limits (`add-hmmscore-job`, #70 and #76), and scores them with the engine's `score()` (`port-hmmscore`, #81; `wire-hmmscore`, #83).
  - The site has HMM scoring's form and results (`add-hmmscore-form`, #71 and #79), and no longer marks it as coming soon.
  - The engine can fetch and verify the HMM library (`add-hmmscore-survey-and-sample`, #66 and #67).
- **refmap's classification endpoint,** `GET /refmap/organisms/{code}/classification` (#73, with #77's follow-ups). The site doesn't use it. It answers the generic error until the classification JSON is built ([runbook-server.md](runbook-server.md#the-apis-data)).
- **The data folder** holds `hmmscore/19/`, 67 GB.
- **The API's container** starts with `--init` ([runbook-server.md](runbook-server.md#the-apis-container)).

## Manual Steps

1. **The library:** the tarball was downloaded on the host with `curl` into the data folder. Then `panther-engine hmmscore data fetch --tarball` ran in the API image, as [The HMM Library](runbook-server.md#the-hmm-library) says. It checked the tarball and every file it kept, so no separate `data verify` was needed. The tarball can be deleted afterwards.
2. **What went wrong:** the first fetch stopped at once with `Permission denied` on its work folder, `.hmmscore-fetch-…`. `fetch` makes that folder in the data folder itself, which root owned, while the container ran as the `panther` user. `chown panther:` on the data folder's top level, not its contents, fixed it. Nothing had been written.

## Timings on the Server

Each run was a fresh `panther-engine hmmscore score --usage --cpu 0` in the API image, with the library mounted read-only:

| Query | Run | Wall time | Peak memory |
| ----- | --- | --------- | ----------- |
| The example, APOE, 317 residues | Just after the fetch | 13.5 s | 63 MiB |
| `titin-10000`, titin's first 10,000 residues | Once | 279.9 s | 5,767 MiB |
| The example | Cold: just after `titin-10000`, with 785 MiB of page cache | 13.6 s | 63 MiB |
| The example | Warm: straight after the cold run | 11.1 s | 63 MiB |

- **`titin-10000` took 22% longer than on Endeavour,** where it took 229.0 s and 231.3 s ([the survey](../parity/hmmscore-library-survey.md#the-port-at-the-residue-limit)). It ran on one of the two CPUs: `vmstat`'s `us` stayed near 50%.
- **It fit only with swap's help.**
  - During the run, free memory fell to about 230 MB, and the page cache to about 780 MB.
  - Swap in use was about 1.2 GB, as other processes were swapped out. There was one 10-second burst of heavy swapping, 13 MB/s in and 20 MB/s out.
  - After the run, swap in use was 0.5 GB, and 6,270 MiB were available.
  - Its peak is under Endeavour's 6,136 MiB because part of it was swapped out, not because it needed less.
- **The cold run read from disk at up to about 630 MB/s** (`vmstat`'s `bi`), and the page cache grew back to 6 GB. Reading `binHmm.h3f`, 4.9 GiB, from disk added about 2.5 s, so whether the library stays cached between jobs matters little.

## The Settings

All five keep their defaults, so divergences 11 and 14 need no row for this server:

| Setting | Value | Why |
| ------- | ----- | --- |
| `PANTHER_API_HMMSCORE_MAX_RESIDUES` | 10,000 | `titin-10000` finishes, in 280 s |
| `PANTHER_API_HMMSCORE_TIME_LIMIT_SECONDS` | 720 | 2.6 times `titin-10000`'s 280 s |
| `PANTHER_API_HMMSCORE_MIN_TIME_LIMIT_SECONDS` | 120 | About 9 times the example's 13.6 s, cold |
| `PANTHER_API_HMMSCORE_MAX_RUNNING` | 1 | `titin-10000` alone takes nearly all the memory. Two at once would need about 12 GiB |
| `PANTHER_API_HMMSCORE_CPU` | 0 | One CPU for `hmmscan` leaves the other for cSNP jobs and the API. Each thread adds memory |

**Not measured:**

- An HMM scoring job beside a cSNP job, whose `blastp` adds its own memory.
- Other sequences of 10,000 residues. Titin hits its own models, of up to 35,040 positions, so it's likely near the worst.

## Rolling Back

- **The API:** start its container from `panther-api:d3fbd39`, the image it ran before. The library under `hmmscore/19/` can stay. That image predates `wire-hmmscore`, so it answers HMM scoring with a `501` and doesn't read the library.
- **The site:** roll it back by the way it was deployed, A or B in [runbook-server.md](runbook-server.md).
