# Design

## Context

See proposal.md for why. This change follows these decisions and doesn't revisit them:

- **[tech-stack.md](../../../docs/design/tech-stack.md), Engine conditions:**
  - 1: a library with a CLI;
  - 2: `core/` first, then one submodule per service;
  - 3: parity tests before porting, with a reference image as the test oracle.

  The change updates two things in that doc: condition 3, for refmap's image, and the Shared Concerns data row, to match the `engine-core` spec.
- **[api-stack.md](../../../docs/design/api-stack.md):** the tooling (uv, Ruff with the `S` rules, basedpyright strict, pytest).
- **`engine-core`'s Data folder requirement:** each service's data is under `<service>/<version>/`. So refmap's data is under `refmap/19/`, as #52 (question 4) answered, not under tech-stack.md's shared `/data/panther/19/`.
- **The interface:** [`add-refmap-job` design](../archive/2026-10-30-add-refmap-job/design.md), decision 3. This change adds `organism` to the result (#52, question 7). The API's input rules are decision 4 there, and `ValueError` mirrors them.
- **#52's answers** (2026-11-05, and the update on 2026-11-06):
  - the organism key is the short code;
  - the data is the 2024-06-20 release, pinned by sha256;
  - the organism list is committed JSON generated from `stats`;
  - each file is saved under its code;
  - the limits stay as they are;
  - every quirk matches the legacy;
  - divergence rows 9 and 10 are approved.
- **Quirk IDs:** [refmap-legacy-behaviour.md](../../../docs/parity/refmap-legacy-behaviour.md).

What the engine already has, from the cSNP work:

| Module | What refmap uses |
| ------ | ---------------- |
| `core/data.py` | `service_folder("refmap", "19", data_dir)`, `DataFolderError`, `MissingDataError` |
| `core/manifest.py` | `read_manifest`, `checksums`, `verify` and `sha256_stream`: a manifest is `files`, which maps each path, from the data root, to its sha256 |

| `tests/conftest.py` | the `data(*services)` marker, `DATA_MANIFESTS`, and `PANTHER_REQUIRE_DATA` |

The legacy lookup is `map_panther.pl` (56 lines). It's the same file at `4fc6a09`, on `master` (`649c85f`), and in the copy `data.pantherdb.org` serves:

```text
classification file (-i)                       gene list (-g)
  chomp: drop the final \n only                  s/\r//g, then chomp
  split /\t/: ($id, $pthr)                       split /\t/: ($id, @rest)
  $pthr{$id} = $pthr       (last line wins)      defined $pthr{$id} ?
                 \                              /
                  +----------> lookup <--------+
                                 |
          "$id\t$pthr\t@rest\n"  or  "$id\tNOHIT\t@rest\n"   (stdout, one per list line, in order)
          "$count1 IDs can be mapped." and "$count2 IDs are not mapped."   (stderr)
```

From the #52 survey of the pinned release:

- **Files:** 1,533, with 22,961,201 lines in all.
- **Lines:** every line is `ID<TAB>value`, ASCII, ending in LF. No ID repeats within a file or across files.
- **Values:** a subfamily, a family, or the text `NOHIT`. `NOHIT` is on 3.7M lines in all, and on 119,131 of the largest file's 246,021 (`ARAVE`).

## Goals / Non-Goals

**Goals:**

- For any classification file and any list of valid IDs, the first two fields of `map_panther.pl`'s output, byte for byte, compared as text.
- The organisms available without a data folder.
- One fetch for developers, CI and servers, with file names every platform can hold.
- M1's acceptance run on the full data, on a developer machine.

**Non-Goals:**

- **Indexing or caching classification files.** A lookup reads one file: about 0.1 s for 100,000 IDs against the largest (#52).
- **Echoing the columns after the ID (`REFMAP-5`),** or the counts on stderr (`REFMAP-12`). The API takes IDs only, and has no counts.
- **A data sample.** The whole release is 157 MB, the size of the cSNP sample, so developers and CI use it as it is.

## Decisions

### 1. Module layout

```text
engine/src/panther_engine/
  core/download.py       download(url, target): moved from csnp/sample.py, unchanged
  csnp/sample.py         imports download from core
  refmap/__init__.py     exports map_ids, RefmapInput, IdMapping, RefmapResult, ORGANISM_CODES,
                         ORGANISM_NAMES, DATA_VERSION, check_data
  refmap/organisms.py    ORGANISM_NAMES and ORGANISM_CODES, read from organisms.json at import
  refmap/organisms.json  generated by `refmap data manifest`, committed
  refmap/mapping.py      the dataclasses, the input checks, reading a classification file,
                         map_ids(), check_data()
  refmap/data.py         the manifest (data.json): fetch, verify, and building data.json and
                         organisms.json from a release
  refmap/data.json       generated by `refmap data manifest`, committed
  refmap/parity.py       the golden cases, the Perl runner, the full run, the comparisons
  refmap/cli.py          map; data fetch, verify and manifest; parity reference, check and full
  cli.py                 + refmap
```

- **`download()` moves to `core/`** because refmap needs the same download. CLAUDE.md puts shared code in `core/`, and one service shouldn't import another's module. Its tests move with it, and `csnp/sample.py` imports it from there.
- **`refmap/__init__.py` imports only `organisms` and `mapping`.** The API imports the package for the organism check (#40), so it must not pull in `tarfile`, `urllib` or the parity code.

### 2. The interface

```python
# panther_engine.refmap
DATA_VERSION = "19"
ORGANISM_NAMES: Mapping[str, str]       # code -> name, in long-name order, read-only
ORGANISM_CODES: frozenset[str]          # ORGANISM_NAMES's codes

@dataclass(frozen=True)
class RefmapInput:
    organism: str
    ids: tuple[str, ...]

@dataclass(frozen=True)
class IdMapping:
    id: str
    panther_id: str | None              # None where the legacy printed NOHIT

@dataclass(frozen=True)
class RefmapResult:
    organism: str                       # the request's, for the job page (#52, question 7)
    mappings: tuple[IdMapping, ...]     # one per input ID, in input order

def map_ids(request: RefmapInput, *, data_dir: Path | str | None = None) -> RefmapResult: ...
def check_data(data_dir: Path | str | None = None) -> None: ...
```

- **`data_dir` is the data root,** as for `score()`. The file is `service_folder("refmap", "19", data_dir) / "panther_classification" / organism`.
- **`ValueError`, before any file is opened,** when:
  - the organism isn't in `ORGANISM_CODES`;
  - there are no IDs;
  - an ID doesn't match `[!-~]{1,64}`, the API's `PRINTABLE` and `LONGEST_ID`.

  There's no cap on the number of IDs (proposal, For review). There's no `InputError` either: every valid request has an answer.
- **`MissingDataError` (divergence 9)** when the organism's file is missing or can't be read. It names the file. The API turns it into the generic `500`, and logs the message.

### 3. Reading a classification file: the Perl's reading, on bytes

- **The file is read as bytes and decoded as Latin-1,** so each byte is one character, as in Perl's byte strings. The pinned data is ASCII; Latin-1 matters only for made-up files.
- **Lines are split on `\n` alone.** An empty element after the last `\n` isn't a line, because Perl's `<FH>` gives none there. A `\r` stays in the line, and so in its value (`REFMAP-3`).
- **Fields are split as `my ($id, $pthr) = split(/\t/, $line)` splits them.** Assigned to two scalars, `split` gets an implicit limit of 3, so a trailing empty field is kept (perlfunc, `split`). Corrected in apply: this decision first said trailing empty fields were dropped, and the reference's goldens showed otherwise (`no-second-field`, 2026-11-06).
  - **ID and value:** the ID is the text before the first tab. The value is the text after it, up to the next tab or the end, or none when the line has no tab.
  - **`A1`** gives `A1` no value. The Perl printed `NOHIT`.
  - **`A1\t`** gives `A1` the value `""`, as does **`A1\t\tPTHR1`**. The Perl printed an empty PANTHER ID, so the port returns `""` too.
  - **An empty line** gives Perl the key `""`. That can't matter, because no empty ID is ever asked for.
- **Only the lines for requested IDs are kept,** in one pass. A later line for an ID overwrites an earlier one (`REFMAP-2`), including a later line with no value.
  - **Memory:** for 100,000 IDs against `ARAVE`, the peak is 26 MB this way, against 45 MB for the whole file in a dict.
  - **Time:** 0.1 s either way, measured on 2026-11-05.
- **Each requested ID then gets, in order:**
  - none, if it has no line or no value;
  - none, if its value is exactly `NOHIT`;
  - otherwise its value as it is, `\r` included.
- **For comparison with the Perl,** a mapping is rendered as `f"{id}\t{panther_id}"`, with `NOHIT` for none. That equals the first two fields of the Perl's line. The Perl always prints a third field, possibly empty, after a second tab (`REFMAP-5`).

*Alternative:* text-mode reading or `splitlines()`. Rejected: both split on `\r`, which would hide `REFMAP-3`.

### 4. The organisms, from committed JSON

- **`organisms.json`** is a list of `{"code", "long_name"}`, in long-name order. That's Python's `sorted`, which matches the website's Java `String.compareTo` order on these ASCII names (`OrganismHelper.java` 223, `MapOrgComparator`). `stats` itself isn't in that order.
- **`ORGANISM_NAMES`** maps each code to a name: the long name split on `_`, with every part but the last joined by spaces, as `MapOrganism.java` (29 to 49) builds its display name. The website then added the code in brackets, and the UI does that for refmap as it does for cSNP's `SPECIES_NAMES`. The mapping is read-only (`MappingProxyType`). `ORGANISM_CODES` is its keys.
- **The long names stay in the JSON** for two reasons: fetch maps each tarball member to its code through them, and the data test compares them with `stats`.
- **JSON, not a literal like `SPECIES_NAMES`:**
  - it has 1,533 entries;
  - it changes with each release;
  - it is written only by `refmap data manifest`, so the code never hand-edits it.

  Decided on #52. The alternative, reading `stats` at startup, was rejected there: the API couldn't validate a request without the data.

### 5. The manifest, and pinning a release

```json
{
  "release": "2024-06-20",
  "version": "19",
  "tarball": {"url": "https://data.pantherdb.org/ftp/generic_mapping/archive/2024-06-20/panther_classifications.tar.gz",
              "sha256": "74821b94...", "bytes": 156535594},
  "stats": {"url": "https://data.pantherdb.org/ftp/generic_mapping/archive/2024-06-20/stats",
            "sha256": "c48ae2f5...", "bytes": 59577},
  "files": {"refmap/19/panther_classification/ABRPR": "...", "...": "...",
            "refmap/19/stats": "c48ae2f5..."}
}
```

- **`files` is in `core/manifest.py`'s format,** so `verify()` and conftest's data marker read it unchanged.
- **`panther-engine refmap data manifest TARBALL STATS --tarball-url URL --stats-url URL`:**
  - **How it reads:** it streams the tarball once without unpacking it, as `csnp/full.py` does. For each member it computes the sha256 and counts the lines and the `NOHIT` lines.
  - **What it checks:** it runs every check in the spec's "Pinning a release". The Windows device names are `CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9` and `LPT0` to `LPT9`, matched in any case.
  - **What it writes:** `data.json` and `organisms.json`, only if every check passes. Keys are sorted and each file ends in a newline, so the same inputs give the same bytes.
  - **Where:** by default the package's own files, as in a developer's checkout.
- **A future release** goes under `refmap/<new version>/`, with a regenerated manifest and organism list. The old folder can stay beside it.

### 6. Fetch: files named by code, never by member name

```text
data.json --> download the tarball and stats       (or --tarball FILE / --stats FILE)
          --> size and sha256 of each == the pin?   no --> stop, name both values, write nothing
          --> stream the tarball. Each member must be a regular file
              panther_classifications/<long name>, with <long name> in organisms.json
                                                     no --> stop, name the member, write nothing
          --> write its bytes to <tmp>/refmap/19/panther_classification/<code>
          --> copy stats to <tmp>/refmap/19/stats
          --> verify <tmp> against files              no --> stop
          --> os.replace each file into <root>/refmap/19/
```

- **First, `verify(root, files)`.** If it passes, nothing is downloaded. That hashes 523 MB, a few seconds.
- **The temporary folder is in the data root,** named `.refmap-fetch-*`, so `os.replace` stays on one filesystem. It's removed on any exit, as cSNP's fetch removes its own.
- **A member's name is never used as a path.** The path comes from the code in `organisms.json`. So `:` in a long name, `..`, absolute paths and links can't reach the filesystem. The tarball's folder is `panther_classifications/`, plural; the published folder and the website's use `panther_classification/`.
- **Every listed file must arrive.** The verify step finds one that didn't.
- **Alternatives,** both rejected on #52 (the update to question 4):
  - **Keep the long names.** Windows can't create ten of them. On NTFS, Python doesn't fail on `name:x`: it writes the data into a hidden stream `x` of a file called `name`.
  - **Replace `:` with `_`.** That makes a third spelling of each name, and needs a rule for every character Windows refuses.

### 7. `check_data()`: presence, not hashes

- **What it checks:** that `refmap/19/stats` is a file, and that `panther_classification/<code>` is a file for every code. That's 1,534 `stat` calls, which take milliseconds.
- **What it raises:** `MissingDataError`, naming the folder and the missing files (a count, and the first few), as cSNP's check does.
- **What it doesn't do:** `verify` is the hash check. The API's startup log calls `check_data`, as it does for cSNP (`api/src/panther_api/main.py` 37 to 47); #40 adds refmap's call there.
- **`map_ids` doesn't call it.** `map_ids` opens only the organism's file, and raises `MissingDataError` when it can't (decision 2).

### 8. The reference image

```text
FROM ${PYTHON_IMAGE} AS refmap-reference-script
  apt: curl
  curl https://raw.githubusercontent.com/pantherdb/RefProteomeMapper/
       4fc6a0953ecf138d9d716ba2641afa4664796a51/map_panther.pl
  sha256sum --check --strict      ee535a9b935f439be29ae2eafda2c9c953b1abf5f4ab5623bcc7da1746919725

FROM engine AS refmap-reference
  apt: perl                       (Debian's; Getopt::Std is core)
  COPY --from=refmap-reference-script map_panther.pl -> /opt/refmap-reference/
```

- **Downloaded at the full commit SHA.** The repository is public, so this is what Engine condition 3 first planned for every service. The pin is the same file on `master` (`649c85f`), in `panther-workspace`, and on `data.pantherdb.org` (checked 2026-11-05 and 2026-11-06).
- **A separate download stage,** as `blast` and `hmmer` have, so curl stays out of the reference image. If `build-with-extra-ca` has merged, the download step takes its CA mount, as every other download does.
- **Built `FROM engine`,** so Perl and the Python harness are in one container. The `api` stage gets neither. CI and compose never build it, as for `csnp-reference`.
- **No self-check.** cSNP's image checks itself against spec §7's transcribed output. No output from `map_panther.pl` was ever published, so there's nothing to check against. Instead, the full run compares the Perl with the port on every line, and the #52 survey read the same files independently.

### 9. Goldens and the parity commands

```text
engine/tests/golden/refmap/
  README.md      each file's source and sha256, and how to regenerate
  cases.json     each case: a name, an organism code or a made-up file, an ID list
  release/       test_geneList, test_geneList_values: from data.pantherdb.org, unchanged
  cases/         hand-made ID lists, and made-up classification files with their lists
  out/           map_panther.pl's stdout for each case, byte for byte
```

- **Against `ENDPU`:**
  - the two release lists;
  - repeats;
  - lower case, `-2` and `.1`;
  - a list whose first ID has no match;
  - IDs from `ARAVE`, and IDs with punctuation such as `;` and `|`.
- **Made-up files:**
  - a repeated ID (`REFMAP-2`);
  - CRLF endings (`REFMAP-3`; `.gitattributes` keeps `engine/tests/golden/**` byte for byte);
  - `A1` alone (no value) and `A1\t` (an empty value), after an earlier value;
  - an empty second field;
  - a third field;
  - a stored `NOHIT`.
- **Divergence cases,** with the reference's output kept as a record. The check expects the port to refuse these:
  - an empty line, and an ID with a space (row 10): `ValueError`;
  - a missing file (row 9): `MissingDataError`.
- **The gene lists** are read as the Perl reads them: every `\r` removed, and the first tab field taken. The same reader serves `refmap map --file`.
- **`panther-engine refmap parity reference`,** in the image, runs `perl map_panther.pl -i FILE -g LIST` for each case through `run_tool()`, and writes `out/`.
- **`parity check`** compares the port with `out/`, line by line, and names the case and the line. pytest calls the same function. The cases on `ENDPU` need `data("refmap")`; the made-up files need no data.
- **`parity full [--seed port-refmap] [--organism CODE ...]`,** in the image, works one organism at a time.
  - **The list:** the file's IDs in file order. Then extras, from `random.Random(f"{seed}:{code}")`: 20 of its IDs repeated, 20 lower-cased, 20 with `-2`, 20 with `.1`, and 20 from the next organism's file.
  - **The run:** it writes the list to a temporary file, runs the Perl, maps the same IDs with `map_ids`, and compares.
  - **The report:** for each organism, the IDs compared and any differences. It exits with 1 if there are any.
  - **The result** is M1's acceptance, recorded in `docs/parity/inputs.md`.

### 10. CI and the data marker

- **`conftest.py`:** `DATA_MANIFESTS["refmap"]` is refmap's `data.json`, and a `refmap_data` fixture gives `data_folder() / "refmap/19"`.
- **`ci.yml`, `engine` job:** a second `actions/cache` step, with path `.data/refmap` and key `refmap-data-${{ hashFiles('engine/src/panther_engine/refmap/data.json') }}`. Then `uv run panther-engine refmap data fetch --data-dir ../.data`. On a cache hit, that only verifies.
- **`engine-image` job:** the same key, and the fetch run in the image into `/fetch`, as for the sample.
- **`api-image`:** unchanged. #40 adds refmap there.
- **The cache size:** the cache holds the unpacked folder, 523 MB, beside the cSNP sample's 622 MB.

### 11. The command line

- **`refmap map --organism CODE (ID ... | --file FILE) [--data-dir DIR] [--json]`:**
  - **Output:** one line per ID, the ID and the PANTHER ID or `NOHIT`, separated by a tab. With `--json`, it prints `{"organism", "mappings": [{"id", "panther_id"}]}` instead.
  - **Errors:** `ValueError`, `MissingDataError`, `DataFolderError` and `OSError` print `panther-engine refmap map: <message>` on stderr, print nothing on stdout, and exit with 1.
- **`refmap data fetch [--data-dir] [--manifest] [--tarball FILE] [--stats FILE]`**, **`data verify [--data-dir] [--manifest]`** and **`data manifest`** (decision 5). `verify` prints `missing: PATH` and `differs: PATH`, as cSNP's does.
- **`refmap parity reference | check | full`** (decision 9).

### 12. Tests

| Marker | What's tested |
| ------ | ------------- |
| None | The reading rules on made-up files. The input checks. The organisms: count, names, order, codes. `data manifest` on small built releases: reproducible, counts disagree, repeated code, device name. `data fetch` on a small built release, with its pins passed in: fresh, already fetched, wrong checksum, unexpected member, local copies, no `:` in names. `data verify`: a changed file. The command line: help, unknown organism. `parity check` on the made-up cases |
| `data("refmap")` | The goldens on `ENDPU`. The data folder against its manifest. The organism list from `stats`, against the committed one. `check_data()`. A whole genome (`ARAVE`). `refmap map --file test_geneList` |

## Risks / Trade-offs

- **[`data.pantherdb.org` is down, or its archive changes]** → The pins fail loudly. CI's cache covers every run with an unchanged manifest. A GitHub release asset is the fallback mirror (proposal, For review).
- **[A future release names members differently]** → `data manifest` regenerates both JSON files from that release. Fetch maps member names through `organisms.json`, so a mismatch stops it before anything is written.
- **[The Perl in the image reads differently from production's]** → `map_panther.pl` uses only `Getopt::Std`, `chomp`, `split` and a hash, whose behaviour hasn't changed in Perl 5 for decades. The full run checks Perl and port against each other on every line.
- **[The CI cache grows by 523 MB]** → Within GitHub's 10 GB per repository. An evicted cache is fetched again from `data.pantherdb.org`.
- **[Moving `download()` touches cSNP code]** → The move is mechanical. Its tests move with it, and the cSNP sample tests still pass.
- **[One large pull request]** → It splits at the data and organisms, then the mapping, goldens and parity (proposal, Size).

## Migration Plan

Nothing in production changes: the API answers `501` until #40. The order:

1. `download()` moves to `core/`. Then the manifest builder and the organism list, fetch and verify, and the CI data step.
2. The reference image and the goldens.
3. `map_ids()`, `check_data()` and the command line.
4. The full run, recorded.
5. The docs, and the approval of rows 9 and 10.

Rollback is reverting the pull request. A fetched `refmap/19/` folder can stay where it is.

- **How long the full run takes in the image.** It's measured in apply, and recorded in the Notes. Whether CI should ever run it, for example weekly, can wait for that number.
